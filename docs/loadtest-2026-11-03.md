# 1,000명 부하·데이터·보안·속도 점검 (2026-11-03)

## 방법
- 운영과 같은 설정 파일·이미지로 **별도 시험 서버**(포트 5290, 별도 DB)를 띄워 시험했다. 운영 데이터에 시험 계정을 남기지 않기 위해서다. 공개 주소(genio.tail6bd481.ts.net)는 보안 헤더·화면 속도만 가볍게 확인했다.
- 사용자 1명 시나리오(요청 25개): 가입 → 내 정보 → 챗 앱 만들기 → 버전 저장 → 공개 배포 → 공개 챗 2번(실시간 응답) → 테스트 실행(워커 처리 완료까지) → 데이터 표 만들기·행 3개·검색 → 웹훅 만들기·호출 → 앱·실행·활동 기록·프로젝트 현황 조회 → 다시 로그인.
- AI 키가 없어 AI 블록은 쓰지 않았다(입력을 그대로 돌려주는 흐름). 실제 AI 호출 시간은 포함되지 않는다.
- 사용자마다 다른 IP를 흉내 냈다(X-Forwarded-For). 이 방식 자체가 속도 제한 우회 문제의 증거다(아래 보안 §).
- 시험 도구: scratchpad의 loadtest.py·security.py·integrity.py·browser_sec.mjs(저장소 밖).

| 60 | **실패 시작**. 공개 챗 500 오류·연결 끊김, 30초 대기. 가입 중간 8.7초 |
| 100 | **서비스 멈춤**. 10분 동안 130명만 가입, 1분에 DB 대기 시간 초과 195건. 부하가 없어지면 약 1분 뒤 스스로 회복 |

원인
- API가 개발용 설정(`uvicorn --reload`, 프로세스 1개)으로 돈다.
- 공개 챗 스트리밍이 답을 기다리는 동안 작업 스레드(기본 40개)를 하나씩 붙잡는다. 스레드가 모자라면 새 요청이 DB 연결을 연 채(idle in transaction) 기다리고, DB 연결 20개가 모두 묶이면 진행 중인 대화도 결과를 못 읽어 30초 뒤 실패한다(서로 기다림).
- 비밀번호 확인(bcrypt)이 같은 프로세스에서 돌아 가입·로그인이 몰리면 모두 느려진다.

## 4. 보안
잘 막힌 것
- 사용자 간 격리: 다른 사용자의 앱·실행·대화·표·웹훅·멤버·활동 기록에 4,000번 접근·수정·삭제 시도 → 모두 403/404. 다른 앱의 대화 기록 읽기, 표 데이터 섞임 없음.
- 토큰: 없음·내용 바꿔치기·서명 없음(alg=none)·갱신 토큰으로 호출 → 모두 401. access 토큰 15분.
- 내부망 호출(SSRF): 127.0.0.1, localhost, api·postgres·redis 컨테이너, 169.254.169.254, [::1], 0x7f000001, 10.0.0.1 → 모두 차단.
- 비밀값: AI 키는 `****abcd`로만 보이고 활동 기록에도 원문 없음. 앱 비밀 환경 값·웹훅 주소 노출 없음.
- SQL 주입 문자열로 데이터가 새지 않음. 저장형 XSS(앱 이름·설명·챗 메시지·마크다운 javascript: 링크·표 값) 실행 안 됨.
- 로그인 오류 문구가 같아 계정 존재 여부가 드러나지 않음. API 문서는 공개 주소로 열리지 않음(이 PC에서만).
- 비밀 키 길이 충분(서명 키 64자, 암호화 키 44자), .env는 git 제외, DB·Redis 포트는 이 PC에서만 열림.

## 6. 개선 순서(제안)
1. 동시 사용자 한계: 운영 설정으로 실행(--reload 끄고 프로세스 여러 개), 공개 챗 스트리밍이 DB 연결·작업 스레드를 붙잡지 않게 바꾸기, 연결 수·대기 시간 조정 → 같은 시험으로 재측정.
2. 로그인 보호(계정·IP별 실패 횟수 제한), 신뢰하는 프록시가 붙인 IP만 쓰기, 공개 챗 제한을 앱별로.
3. 비밀번호 규칙, 보안 헤더, 라이브러리 업데이트, 데모 계정 정리.
4. 자동 백업(매일 pg_dump, 보관 기간)과 실행 기록 보관 기간 규칙.
